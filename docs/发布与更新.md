# 发布与更新

从 0.2.1 起，两版应用优先读取 `https://hcx-grass-star.github.io/niuma-macos/latest.json`。静态清单有效时不请求 GitHub REST API；清单缺失、超时、网络失败或内容无效时，再请求 `https://api.github.com/repos/Hcx-grass-star/niuma-macos/releases/latest`。双源失败会明确报错，不冒充“已是最新版”。

## 分支与源码归档要求

正式发布必须满足以下一种源码归档方式，不能仅把代码留在个人开发分支、本地工作区或标签中：

- **默认使用发布分支**：从已验证的源码提交创建并推送 `release/<版本号>`，例如 `release/0.3.3`，然后在同一提交上创建 `v<版本号>` 标签、构建安装包并发布。
- **合并主线后发布**：将发布代码合并到远端 `main`，保留主线已有功能，对合并结果完成验证后，从对应提交构建并发布。

采用发布分支时，不要求发布当次立即合并 `main`。后续合并不得覆盖 `main` 独有改动。`codex/update-feed` 只托管更新源，不能代替源码归档。

安装包、平台 CI 和发布标签必须对应同一份已验证源码。已发布标签不可移动，发布历史不可强推覆盖；新代码需要重新构建并发布新版本。已发布版本补建 `release` 分支时，必须以原标签的源码提交为起点；可以追加规范文档，但不能借此改写标签或重传安装包。

## 发布步骤

0. 确定源码归档方式和版本。默认创建并推送对应的 `release/<版本号>`；若采用 `main` 路径，先完成合并。后续版本同步与验证均在所选分支完成，最终源码提交须推送远端，再用于打包、平台 CI 和标签。

1. 同步版本号：`Resources/Info.plist` 的 `CFBundleShortVersionString`、`package.json`、`package-lock.json` 的顶层和根包版本、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml`，同时递增原生 `CFBundleVersion`。版本使用三个数字段，例如 `0.2.1`。
2. 执行 `npm run test:core` 和 `npm run test:updates`。验证收入、静态主源、备用 API、平台筛选、版本和错误状态。
3. macOS 执行 `bash scripts/package-release.sh`。Windows 在 Windows 开发机或现有 Windows 构建工作流构建，并在对应平台安装验收。
4. 执行 `npm run sign:updates -- <安装包路径...>`，为最终文件生成公开附件：原生 ZIP 的 `.update.json`，Tauri `.exe` / `.msi` / `.app.tar.gz` 的 `.sig`。签名绑定版本，Tauri 客户端启用 `requireSignedVersion`。本机 `~/Library/Application Support/niuma-release-keys/` 的私钥必须单独备份，绝不提交或上传。在本仓库创建正式 Release，例如 `v0.3.0`，填写说明并上传已验证安装包和公开签名附件；不要勾选预发布。仅推送标签或上传 Actions Artifact 不等于正式发布。
5. 正式发布及安装包上传完成后，执行 `npm run publish:updates`。此命令使用发布者本机已有的 `gh` 登录，读取真正的 latest 正式 Release 和已上传安装包，以同一 Git tree/commit 原子更新 `codex/update-feed` 分支的 `latest.json`、原生 `appcast.xml` 和 `tauri-updater.json`；可先运行 `npm run publish:updates -- --dry-run` 预览。凭据只在发布机器使用，客户端不嵌入 Token。
6. 等待 GitHub Pages 部署完成，读取上述公开 `latest.json`，确认版本、发布页及安装包。Pages/CDN 可能有短暂缓存（本次观察到 `max-age=600`），不能把仅提交清单当作部署完成。最后用已具备此检查逻辑的低版本应用手动检查、下载并验证。
7. 重新获取远端 `main`、对应 `release/<版本号>` 和发布标签，确认标签对应的源码提交被至少一个归档分支包含（可使用 `git merge-base --is-ancestor <发布提交> <远端分支>` 验证）。确认源码归档、正式附件、签名和公开更新源后再报告发布完成；报告中列出归档分支或 `main` 合并提交及尚未验收的项目。

静态站点已配置为从 `codex/update-feed` 分支根目录发布；该分支托管公开版本清单、签名更新源、`.nojekyll` 和简单下载入口，与工作代码分离。后续普通发布完成签名和上传后按第 5 步同步，分支提交会触发 Pages 部署。脚本拒绝回退清单版本，使用分支快进更新防止竞争覆盖；重复发布相同内容不产生提交。没有设置自动发布工作流。

## 清单与安装包

清单字段为 `version`、`notes`、`url`（正式发布页），以及可选的 `macos` / `windows` 直接安装包 URL。没有某平台安装包时省略该字段，客户端明确显示该平台暂不可用。只允许本仓库、匹配标签和平台扩展名的地址；说明作为纯文本显示。

- macOS：`.dmg`，或文件名包含 `macOS`（忽略大小写）的 `.zip`。建议英文文件名 `niuma-0.2.1-macOS-universal.zip`，避免 GitHub 自动移除中文字符。
- Windows：`.exe` 或 `.msi`。
- 0.3.0 的“安装更新”使用签名更新源；“手动下载”继续打开本仓库版本页。Tauri 根据系统、CPU 和安装器类型选包，原生 Sparkle 使用通用 ZIP。
- Tauri macOS 使用 `APPLE_SIGNING_IDENTITY=- npm run tauri:build` 打包，再压缩 `.app` 为 `.app.tar.gz` 并签名，例如 `tauri-niuma-0.3.0-macOS-aarch64.app.tar.gz`。未构建的架构不出现在更新源中；不能给 Tauri 发送 Swift 原生 ZIP。

## 升级及故障边界

- 0.2.x 没有自动安装器，首次升级到 0.3.0 需要手动下载并打开新版；之后可在应用内安装未来版本。
- 手动打开新版 macOS 包会先复制和验签、退出对应旧进程、归位覆盖，再等待新版启动。成功后才回收旧包；新版启动失败则恢复旧包并重启。权限不足、旧进程拒绝退出时停止并提示，不强杀、不删除配置、不静默降级。
- 清理只处理系统注册的同 Bundle ID 较旧应用，以及哈希匹配的本次同版本下载源；不递归扫描磁盘，不删除较新或同版本未知构建、压缩包、其他应用或工资目录。开发构建默认不自动迁移。
- 当前临时签名分发包首次打开仍可能需要用户在系统设置批准。系统目录权限、登录启动随路径迁移和其他系统版本需要对应环境单独验收。两种 macOS 实现不互相转换配置格式。
- 原生版本来自包内 Info.plist；Tauri 版本来自 `AppHandle.package_info()`；浏览器预览清单由 `npm run sync:frontend` 从 package.json 生成。
- 原有自动开关、24 小时限频和手动检查不变。每个来源最多等待 10 秒，只有主源失败才发起备用请求；网络失败不影响收入计算。
- 静态托管消除了对匿名 REST API 额度的直接依赖，但不是断网或所有托管服务永不受限的保证。双源都失败时保留错误，不保存工资或排班到远端。
- 开发分发包使用临时签名；更新检查不替代 Apple Developer ID、公证或 Windows 分发验收。

安装实现依据：[Sparkle 集成](https://sparkle-project.org/documentation/)、[Sparkle 安全与签名](https://sparkle-project.org/documentation/security/)、[Tauri updater](https://v2.tauri.app/plugin/updater/)。验证命令：`npm run test:installation`、`python3 scripts/test-macos-installation.py`、`python3 scripts/test-sparkle-installation.py`。Tauri 真实进程验证在具备本地 Rust 缓存的环境运行 `python3 scripts/test-macos-installation.py --tauri`。
